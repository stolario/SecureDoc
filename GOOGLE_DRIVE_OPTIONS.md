# Варианты интеграции SecureDoc с Google Drive

## Цель и неизменные требования

SecureDoc должен сохранять в Google Drive только готовый файл `.sdoc`.

- Пароль документа, ключи шифрования, открытый HTML и изображения не покидают браузер.
- Для защищённого документа в Drive попадает уже зашифрованный контейнер.
- Google видит метаданные файла: имя, размер, время изменения и аккаунт владельца.
- Рекомендуемый OAuth scope — `https://www.googleapis.com/auth/drive.file`. Он разрешает
  приложению работать только с созданными им или явно выбранными пользователем файлами, а не со
  всем содержимым Google Drive.
- Публичный OAuth Client ID находится в клиентском коде. Это идентификатор приложения, не секрет.
- OAuth Client Secret нельзя помещать в браузерный код.

## Вариант 1. Полностью без backend

### Схема

```text
браузер с SecureDoc
    ├── Google Identity Services → временный access token
    └── Google Drive REST API    → загрузка/чтение зашифрованного .sdoc
```

SecureDoc остаётся набором статических файлов. Авторизация выполняется официальной браузерной
библиотекой Google Identity Services по Token Model. После согласия пользователя Google возвращает
короткоживущий access token прямо в браузер. SecureDoc использует его в запросах к Drive API.

Authorization Code + PKCE для этого варианта самостоятельно реализовывать не следует. В модели
Google полноценный Authorization Code Flow завершается на backend, который принимает code и
обменивает его на access/refresh tokens. Для чистого браузерного приложения предназначен Token
Model.

### Пользовательский поток

1. Пользователь нажимает `Подключить Google Drive` или `Сохранить на Google Drive`.
2. Google показывает выбор аккаунта и окно согласия.
3. SecureDoc получает временный access token и держит его только в памяти вкладки.
4. `Sdoc.encode(...)` формирует `.sdoc` локально.
5. Зашифрованный `Blob` загружается напрямую в Google Drive.
6. SecureDoc запоминает `fileId` текущего файла в памяти, чтобы следующие сохранения обновляли его.
7. После закрытия или перезагрузки вкладки пользователь при необходимости снова предоставляет
   доступ. Ранее выданное согласие обычно не требуется подтверждать заново, но получение нового
   access token должно начинаться с действия пользователя.

### Что потребуется в Google Cloud

1. Проект Google Cloud, например `SecureDoc`.
2. Включённый Google Drive API.
3. Настроенный OAuth consent screen.
4. OAuth Client ID типа `Web application`.
5. Зарегистрированные Authorized JavaScript origins для каждого адреса приложения, например:

   ```text
   http://localhost:8637
   https://securedoc.example.com
   ```

6. Scope `https://www.googleapis.com/auth/drive.file`.
7. Для разработки — аккаунты разработчиков в списке Test users. Перед публичным запуском —
   публикация OAuth-приложения и необходимая базовая проверка Google.

### Изменения в SecureDoc

- Добавить кнопку подключения и состояние Google-сессии.
- Подключить Google Identity Services.
- Добавить Drive REST-клиент для создания, обновления и чтения `.sdoc`.
- Для выбора существующего файла использовать Google Picker с фильтром `.sdoc` / MIME приложения.
- Ввести цель сохранения: локальный `FileSystemFileHandle` или Google Drive `fileId`.
- Сохранить текущую модель `Save`, `Save as…`, `Save a copy…` для обеих целей.
- Обработать `401`, истечение токена, отмену OAuth, потерю сети и конфликт версий файла.
- Расширить CSP только необходимыми адресами Google. Это ослабляет нынешнюю полностью локальную
  сетевую изоляцию, поэтому разрешения должны быть максимально узкими.
- Не хранить access token в `localStorage`, IndexedDB, URL или самом `.sdoc`; держать его в памяти.

### Преимущества

- Нет своего сервера, базы пользователей, сессий и серверных секретов.
- Нет передачи документов через инфраструктуру SecureDoc.
- Минимальные эксплуатационные расходы.
- Хорошо соответствует текущей архитектуре приложения.

### Ограничения

- Нужен стабильный HTTP(S)-origin. Запуск через `file://` для OAuth практически непригоден.
- Токен короткоживущий; иногда пользователю придётся снова нажать кнопку подключения.
- Нельзя выполнять фоновую синхронизацию после закрытия вкладки.
- CSP должна разрешить Google Identity Services, Google APIs и, при использовании Picker, его frame.
- Блокировщики third-party cookies/popups и корпоративные политики могут мешать авторизации.

### Рекомендация

Это основной вариант для SecureDoc. Он сохраняет принцип «документом владеет браузер» и не создаёт
новой доверенной стороны, имеющей доступ к пользовательским токенам или файлам.

## Вариант 2. Backend только раздаёт статику и ничего не хранит о пользователе

### Схема

```text
статический backend SecureDoc
    └── отдаёт index.html, css/, js/, icons/ и публичную конфигурацию

браузер
    ├── Google Identity Services → временный access token
    └── Google Drive REST API    → загрузка/чтение зашифрованного .sdoc
```

Backend не принимает документы, не проксирует Drive API, не принимает OAuth authorization code,
не хранит refresh/access tokens, cookies, пользовательские профили или журналы действий. Вся работа
с Google остаётся прямым обменом между браузером пользователя и Google.

Это не отдельная OAuth-архитектура: авторизация остаётся такой же, как в варианте 1. Отличается
только способ доставки самого приложения.

### Что делает backend

- Отдаёт только разрешённые статические ресурсы приложения.
- Предоставляет стабильный HTTPS-origin, зарегистрированный в Google Cloud.
- Выставляет CSP и остальные security headers обычными HTTP-заголовками.
- Может отдавать публичную конфигурацию окружения, например OAuth Client ID и feature flag Drive.
- Не устанавливает пользовательскую сессию и не пытается идентифицировать пользователя.
- Не логирует query string, OAuth-данные или имена документов. Обычные access-логи следует
  минимизировать или отключить, если заявлено «ничего не знает о пользователе».

### Чего backend не должен делать

- Не принимать или хранить `.sdoc`.
- Не принимать access token в заголовках, cookie, query string или теле запроса.
- Не хранить Client Secret: в этой архитектуре он не нужен.
- Не обменивать authorization code на токены.
- Не проксировать запросы к Google Drive.
- Не внедрять аналитику, crash reporting или внешние шрифты/скрипты без отдельного решения о
  приватности.

### Почему здесь не нужен Authorization Code Flow

Чтобы корректно использовать серверный Authorization Code Flow, backend должен как минимум принять
authorization code, проверить запрос и обменять code на токены. Для длительной работы ему нужно
безопасно хранить refresh token, то есть знать пользовательскую OAuth-сессию. Это уже противоречит
условию «только отдаёт статику и ничего не хранит/не знает о пользователе».

Теоретически backend может обменять code без постоянного хранения, но тогда токены придётся вернуть
в браузер либо потерять после запроса. Такая схема сложнее Token Model, не даёт полезного преимущества
и увеличивает поверхность атаки. Поэтому для stateless static backend используется браузерный Token
Model, а не искусственный серверный OAuth flow.

### Преимущества относительно варианта 1

- Предсказуемый HTTPS-адрес и отсутствие проблем `file://`.
- CSP и другие security headers задаются надёжнее, чем через `<meta>`.
- Проще менять публичный Client ID между dev/staging/prod без правки основной сборки.
- Можно строго гарантировать, что сервер раздаёт только `index.html`, `css/`, `js/` и `icons/`.
- Проще обновлять приложение и исправлять интеграцию без распространения архивов пользователям.

### Ограничения

- Сервер всё равно видит сетевые метаданные обычного HTTP-запроса: IP-адрес, время обращения,
  User-Agent — если инфраструктура или reverse proxy их журналирует.
- Появляются расходы на домен, TLS, hosting и обновления сервера.
- Фоновой синхронизации и refresh token по-прежнему нет.
- Компрометация сервера позволяет подменить JavaScript, который затем работает с access token.
  Нужны защищённый deployment, TLS, CSP и контроль целостности релизов.

### Рекомендация

Этот вариант предпочтительнее для публичного размещения: функционально данные и OAuth остаются
полностью клиентскими, но SecureDoc получает стабильный HTTPS-origin и управляемые security headers.
Для локального/offline использования можно одновременно оставить обычную загрузку файлов без Drive.

## Итоговый выбор

| Критерий | Без backend | Static-only backend |
|---|---|---|
| OAuth-модель | GIS Token Model в браузере | GIS Token Model в браузере |
| Client Secret | Не нужен | Не нужен |
| Документы проходят через сервер SecureDoc | Нет | Нет |
| Сервер хранит токены/пользователей | Сервера нет | Нет |
| Стабильный HTTPS-origin | Нужен внешний static hosting | Да |
| Работа через `file://` с Drive | Не рекомендуется | Не используется |
| Фоновая синхронизация | Нет | Нет |
| Сохранение локальных `.sdoc` | Да | Да |

Практическая рекомендация: реализовать один клиентский модуль Google Drive на GIS Token Model и
поддержать два способа доставки SecureDoc. Для пользователя поведение будет одинаковым; static-only
backend даст стабильный production-origin, а полностью статический пакет сохранит автономный режим.
